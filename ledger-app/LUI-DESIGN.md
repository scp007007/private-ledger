# 自然语言交互（LUI）接入评估

LUI 按自然语言交互理解。本文件是设计评估，尚未实现或安装模型。

## 结论与推荐

现有 Flutter + FastAPI + SQLite 结构适合增加 LUI，无需重写账本和同步模块。文字查询/总结工作量适中；可靠的多轮修改、离线自然语言理解和语音输入需要额外设计。

推荐：手机文字入口 → 已认证 FastAPI 助手接口 → 受约束的意图结构 → 账本服务函数 → 结果卡片。优先采用 Windows 本地 Ollama 推理，禁用云功能，仅监听本机；手机继续只连接账本服务。模型选择需依据电脑内存、显存、中文理解和实测延迟，不在评估阶段下载模型。

Ollama 支持 JSON Schema 结构化输出与工具调用，仍须由 Pydantic 验证并按白名单执行。模型只负责理解请求和解释结果，金额汇总、日期范围、实际消费口径和退款计算由确定性账本逻辑负责。

本机只读检查得到可用物理内存约 15.3 GiB，显卡型号包含 Radeon 780M 与 RX 7600M XT。建议先验证小型中文模型，记录意图准确率、结构校验通过率与实际延迟；尚未验证 AMD 加速驱动和模型兼容性，不预先承诺速度。初版不需要向量数据库或复杂 Agent 框架，使用现有 FastAPI/Pydantic 加受控服务调用即可。

官方 Windows ROCm 列表未直接列出 RX 7600M XT，不能把桌面版 7600 XT 的支持等同于移动型号；可后续验证 Vulkan 后端，失败时评估 CPU 回退。具体见 https://docs.ollama.com/gpu 。

## 分阶段范围

1. 查询与总结：例如“上个月餐饮实际消费多少”“列出本月未分类交易”“今年比去年多花在哪里”。结果包含时间范围、统计口径、数据更新时间及可点击流水入口。同比功能需要增加确定性对比服务，不能只靠模型猜测。
2. 修改建议：例如“把这几笔地铁支出改为交通”。返回目标交易、当前版本、字段差异、笔数及金额，用户确认后才走既有编辑流程；冲突重新预览，幂等 operation_id 防止重试重复执行。不得让后端助手绕过手机待同步队列造成缓存不一致。
3. 自然语言补记：例如“今天午饭28元”。0.4.0 已增加手动新建交易、唯一标识、幂等创建及离线同步队列；后续 LUI 可以生成填写草稿，经用户确认后复用手动新增流程，不直接写数据库。
4. 语音：在文字闭环稳定后增加。离线要求下优先本地语音识别，音频需有独立的权限、留存和清理策略；不能假定系统听写一定在本地处理。

## 意图与数据边界

初期白名单仅开放 query_transactions、get_month_report、get_year_report、propose_transaction_edits。禁止模型生成并直接执行任意 SQL、Python 或 Shell。拒绝不支持的操作，对“这些”“大额”等歧义先追问。商家名和备注作为不可信数据处理，不能把其中的指令当成模型系统指令。

查询以参数化结构表达，如 period、category、source、direction、excluded；服务端验证日期、类别和分页上限。总结只取必要的聚合和有限明细，不默认把全部原始流水塞进上下文。会话不记录令牌；默认不持久化原文日志，保留会话需可清除并明确范围。

## 离线与隐私

本地模型运行在电脑上，所以手机离开服务后无法继续调用该模型。离线可提供固定规则支持的本机查询、读取缓存和暂存输入；恢复后须重新确认执行条件，尤其写操作不能静默补执行。离线结果标记数据更新时间，遵循现有缓存月报口径，不暗示它已包含所有待同步修改。

保持自有设备保存数据的要求时，默认采用本地推理。云模型可做可替换适配器，但接入前需用户另行选择，明确发送字段；“脱敏”不能保证匿名。模型权重和运行时独立存放、按需安装，手机 APK 不捆绑大模型，电脑模型存储会增加且需实测。

## 验收重点

统计结果必须与原生报表一致；相对日期按用户账本时区解释；红包、转账、退款跨月口径明确；歧义不得直接写入；修改需确认且保留离线队列/冲突保护；模型不可用时保留普通界面并给出明确提示。
